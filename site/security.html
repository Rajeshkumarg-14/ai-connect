Security and verification

Connect is designed around local coordination, scoped capabilities, explicit approval, and visible recovery—not a claim of perfect security.

Updated 2026-11-12 · Rajesh Kumar G and Connect contributors

Runtime protections

  • Loopback binding and exact Host/Origin validation.
  • Authenticated local requests and separately scoped agent capabilities.
  • Room-scoped tasks, files, findings, and messages.
  • Text rendering of untrusted conversation content.
  • Bounded request sizes, uploads, queues, output, turns, and handoffs.
  • Explicit legal acceptance and human plan approval.
  • Cancellation, persisted failure states, and deliberate retry.

Checksums and integrity

Release preparation creates SHA-256 manifests. Run npm run integrity:verify to compare local files with the recorded manifest. Use a manifest obtained from a trusted source. Checksums detect mismatches; they do not verify who produced a release, detect all malware, or protect against replacement of both the data and its manifest. No digital signing claim is made.

Scenario tests

The local suite uses deterministic fixtures to exercise coordination, quota handoffs, notifications, invalid input, authentication, uploads, transcript paging, persistence, queue pressure, timeouts, and cancellation. Each scenario becomes an actual executable case. Simulated cases do not establish that every live provider, OS, browser extension, or native bridge version behaves the same way.

Outside the boundary

Connect is not a sandbox for hostile local programs. Processes running as you, administrators, compromised extensions, independently configured CLI hooks/tools, and provider services can act outside the connector’s boundary. Your data is not encrypted at rest by Connect. Do not expose the local app port publicly.

Report privately first

Do not publish secrets, private session transcripts, or exploit details in an ordinary issue. Ask the maintainer at rajeshkumarg.com for a private reporting route before sharing sensitive details. The planned GitHub repository’s private reporting settings must be confirmed after publication. No private mailbox, bug bounty, or response deadline is claimed here.

Publication status

The project and static site are being prepared locally. A public repository may already exist, but this workflow will not push source or deploy Pages until the owner instructs it to. Review the release inventory, tests, license notices, and checksum output before publication.
